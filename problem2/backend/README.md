# MetaboQuest Problem 2 backend

Spring Boot backend for turning a research paper into a source-traceable Instagram content package. It ingests a PDF or public HTTPS article, extracts page-level evidence, generates four content specifications, and blocks publication until a reviewer approves every claim.

No frontend files are used or changed by this service.

## Implemented pipeline

```text
PDF / HTTPS article
        ↓
safe ingestion + SHA-256 deduplication + page text
        ↓
AI structured generation OR deterministic extractive fallback
        ↓
server-side quote/page verification
        ↓
claims + carousel + static + reel storyboard + caption
        ↓
doctor claim review → package approval → approved assets
```

Important boundaries:

- Approved packages can be rendered as brand-aligned carousel/static PNGs, carousel PDF/ZIP archives, reel frames, WAV voiceover, SRT/VTT subtitles, Canva-compatible JSON and complete export bundles.
- The scheduling and publishing endpoints provide an auditable prototype workflow; a real social-platform connector still requires that platform's production credentials and approval process.
- The reel includes timed scenes, voiceover, subtitles, b-roll prompts, duration and music direction. No synthetic medical imagery is generated by this service.
- The fallback uses only directly extracted English sentences. Hindi/Hinglish generation is enabled only when an AI provider is configured.
- `estimatedHumanMinutes` is a 12-minute workflow target, not a measured study result. Audit timestamps are retained so actual reviewer effort can be measured later.
- No asset can become `APPROVED` until all linked claims have verified quotes and explicit reviewer approval. Each package includes an authenticated source-download URL, exact page and evidence quote.

## Run

Java 21 and PostgreSQL are required. Export the variables shown in `.env.example`; do not paste secrets into source files.

```bash
./mvnw spring-boot:run
```

`application.properties` remains the existing database configuration and was not modified by this implementation. Flyway creates the pipeline schema. The only anonymous endpoint is `GET /actuator/health`.

## AI modes

With no `AI_API_KEY`, `ExtractiveAiGateway` produces grounded English drafts so local development does not require a paid API. With a key, `CompatibleAiGateway` calls `${AI_BASE_URL}/chat/completions` with a structured JSON schema and the configured `AI_MODEL`.

The provider prompt treats the paper as untrusted data, limits output to five claims, applies Steer’s voice, and requires verbatim evidence plus page numbers. Model output is not trusted: the backend normalizes and locates every quote in the corresponding stored page before saving anything. The adapter uses the developer-message and structured-output fields documented in the [official OpenAI Chat API reference](https://developers.openai.com/api/reference/resources/chat).

## Authentication

Send `X-API-Key`:

- `PIPELINE_API_KEY`: ingestion, generation, batches and read endpoints.
- `REVIEW_API_KEY`: doctor-review endpoints and read endpoints.

If either environment variable is absent, that role cannot authenticate. The keys should be distinct.

## API workflow

Upload a PDF:

```bash
curl -X POST http://localhost:8080/api/v1/papers/upload \
  -H "X-API-Key: $PIPELINE_API_KEY" \
  -F "file=@paper.pdf" -F "title=Optional title"
```

Or ingest a public HTTPS link:

```bash
curl -X POST http://localhost:8080/api/v1/papers/from-url \
  -H "X-API-Key: $PIPELINE_API_KEY" -H "Content-Type: application/json" \
  -d '{"url":"https://example.org/research-paper"}'
```

Generate the content package:

```bash
curl -X POST http://localhost:8080/api/v1/papers/PAPER_ID/generate \
  -H "X-API-Key: $PIPELINE_API_KEY" -H "Content-Type: application/json" \
  -d '{"language":"en","audience":"Adults in India curious about metabolic health"}'
```

Review each returned claim, then approve the package:

```bash
curl -X POST http://localhost:8080/api/v1/review/packages/PACKAGE_ID/claims/CLAIM_ID \
  -H "X-API-Key: $REVIEW_API_KEY" -H "Content-Type: application/json" \
  -d '{"approved":true,"actor":"Dr Reviewer","note":"Checked against the quoted page"}'

curl -X POST http://localhost:8080/api/v1/review/packages/PACKAGE_ID \
  -H "X-API-Key: $REVIEW_API_KEY" -H "Content-Type: application/json" \
  -d '{"decision":"APPROVED","actor":"Dr Reviewer"}'
```

Batch up to 20 already-ingested papers:

```bash
curl -X POST http://localhost:8080/api/v1/batches \
  -H "X-API-Key: $PIPELINE_API_KEY" -H "Content-Type: application/json" \
  -d '{"paperIds":["PAPER_UUID_1","PAPER_UUID_2"],"language":"en"}'
```

The batch returns `202 Accepted`; poll `GET /api/v1/batches/{id}`. Each paper runs in its own transaction, so one failure does not discard successful packages.

## Safety and reliability

- 20 MB input limit, encrypted/scanned PDF detection, filename sanitization.
- Public HTTPS-only URL ingestion with redirect revalidation and private/local address blocking.
- Source documents deduplicated by SHA-256.
- JSON-schema AI output plus independent evidence validation.
- Immutable prompt version stored with each package.
- Separate pipeline/reviewer roles and append-only review events.
- PostgreSQL constraints for state, JSON shape and confidence ranges.
- Async bounded batch executor and per-paper transactions.
- No automatic publishing: the doctor gate is mandatory.
